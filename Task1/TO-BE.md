# TO-BE: Эволюция архитектуры AdScale

## 1. Decision Matrix для AdScale

| Фактор                                                                                      | Вывод                                                                                                                                |
|---------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------|
| Команда 10–50 человек (35 чел.)                                                             | **Модульный монолит** оптимален, **Микросервисы** - возможно                                                                         |
| Жёсткий дедлайн — 3 месяца и 1 год, ограниченный бюджет                                     | **Монолит/Модульный монолит** - нет времени на полную декомпозицию                                                                   |
| Разные SLA для компонентов (аукцион/ставки ≤80–100 мс критично; статистика/аналитика — нет) | **Микросервисы** (Auction/Bidding, Statistics) - разные требования по latency                                                        |
| Нет выделенного DevOps/SRE, нет контейнеризации, деплой вручную                             | **Микросервисы не подходят** для всей системы сразу, так как сейчас в команде низкая эксплуатационная зрелость                       |
| Разные технологии (C++/Go/Python/Node)                                                      | **Модульный монолит/Микросервисы** - компоненты технологически разделены                                                             |

**Вывод по матрице**: наиболее реалистичный подход для AdScale — модульный монолит с точечным выделением наиболее критичных и нагруженных компонентов (Auction Engine / Bidding и Statistics Service) в отдельно масштабируемые единицы, и постепенный переход на микросервисы через год. 

Полный монолит не подходит из-за разных SLA и необходимости независимого масштабирования. Полные микросервисы не подходят на данный момент из-за сроков, бюджета и отсутствия SRE и зрелой практики DevOps.  

При этом оставить монолит как есть нельзя, так как система уже работает на пределе (15 000 RPS, P95 110–120 мс) и запаса производительности нет. При этом ожидается существенный рост нагрузки после подключения DSP-платформы и без структурных изменений в системе AdScale выполнить SLA партнёра (≤80 мс, без простоев) будет нельзя. Необходимо независимое масштабирование Auction Engine и Statistics Service и разделение критичных/некритичных потоков, а в монолите с общим процессом и общей БД это архитектурно недостижимо. Также один экземпляр PostgreSQL в текущей системе - это узкое место и точка отказа.  

Переписать систему сразу на микросервисы не получится, так как ближайший срок промежуточного решения - 3 месяца, нет контейнеризации, деплой ручной, нет выделенных SRE, есть требование непрерывности обслуживания текущих клиентов.

## 2. Рекомендуемый подход

Для достижения бизнес-целей предлагается для промежуточного решения (3 месяца):

**Стиль: модульный монолит + выделение двух сервисов с помощью Strangler Fig**

| Компонент (AS-IS)                                                    | Решение                                                                                                                                                                          |
|----------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Auction Engine                                                       | Выносится в отдельный масштабируемый **Bidding Service**; синхронные вызовы к БД в hot path заменяются на кеш (campaign/bid data) — закрывает требование ≤80–100 мс и 18 000 RPS |
| Statistics Service                                                   | Запись переводится на **очередь** (буферизация событий кликов/показов), асинхронная запись в БД — снимает write-конкуренцию с OLTP                                               |
| Analytics Service                                                    | Переводится на **read-replica** PostgreSQL — устраняет блокировки транзакционных запросов                                                                                        |
| Ad Server, Delivery Service, Financial Service, Advertiser Dashboard | Остаются в монолите, но выделяются как отдельные модули с чёткими границами — подготовка к дальнейшей декомпозиции                                                               |
| Инфраструктура                                                       | Базовая контейнеризация — только для вынесенных Bidding и Statistics сервисов                                                                                                    |


Для целевой архитектуры (через год):

**Стиль: микросервисы + событийная архитектура**

- Продолжение Strangler Fig: оставшиеся модули монолита (Ad Server, Delivery, Financial, Advertiser Dashboard) выносятся в независимые сервисы со своими БД/репликами.
- Выделяется отдельный Campaign Service — source of truth для кампаний, бюджетов, ставок.
- Фреймворк Kafka для событий кликов/показов и межсервисной интеграции. Синхронным остаётся только критичный путь аукциона.
- Полная контейнеризация и оркестрация, автоматизированный деплой (взамен ручного).
- Горизонтальное масштабирование каждого сервиса под 50 000 RPS.
- Мультирегиональное развёртывание для отказоустойчивости и SLA 99,9%.
