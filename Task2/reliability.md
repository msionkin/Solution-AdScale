# Паттерны надёжности 

Описание паттернов отказоустойчивости для целевой архитектуры AdScale. Цель — удержать SLA DSP-партнёра (время ответа ≤ 80 мс) при отказах и деградации отдельных компонентов, не роняя весь путь аукциона.

Базовый принцип для критичного пути: **fail-fast**. На аукционе бюджет времени мал (≤ 80 мс), поэтому лучше быстро вернуть `no-bid`, чем ждать и нарушить SLA по latency для всех запросов.

## 1. Обзор паттернов

| Связь                                      | Паттерны надёжности                                                                   |
|--------------------------------------------|---------------------------------------------------------------------------------------|
| DSP-партнёр → API Gateway                  | Rate limiting (429 + `Retry-After`), Circuit Breaker                                  |
| API Gateway → Ad Server                    | Circuit Breaker (open → `no-bid`, half-open восстановление)                           |
| Ad Server → Bidding Service (gRPC)         | Deadline 30–40 мс, fail-fast → `no-bid`, Circuit Breaker на gRPC-клиенте, HealthCheck |
| Bidding Service → Kafka (`auction-events`) | Асинхронная публикация, retry с backoff + jitter, буфер продюсера                     |
| Advertiser Dashboard → Financial Service   | Idempotency key, retry с backoff + jitter (безопасно за счёт идемпотентности)         |
| Campaigns → Bidding (`campaign-changes`)   | Kafka (at-least-once), повторная обработка из топика                                  |

## 2. Circuit Breaker

Circuit Breaker применяется в двух местах.

### 2.1. Граница: API Gateway → Ad Server
См. `api-gateway.md`. NGINX + Lua (или NGINX Plus health checks): при превышении порога ошибок/таймаутов от upstream Circuit Breaker переходит в `open`, партнёру сразу возвращается `no-bid`; периодический `half-open` для авто-восстановления.

### 2.2. Межсервисный вызов: Ad Server → Bidding Service
gRPC-клиент Ad Server оборачивает вызов `EvaluateAuction` в Circuit Breaker:
- **Closed** — нормальная работа, вызовы проходят.
- **Open** — при превышении порога ошибок/таймаутов за скользящее окно вызовы к Bidding не делаются, Ad Server немедленно возвращает `no-bid` (не тратит latency-бюджет на заведомо неудачный вызов).
- **Half-open** — пробные вызовы для автоматического восстановления; health-сигналом служит gRPC `HealthCheck` (`bidding-service.md`).

Пороговые значения (открытие при доле ошибок X% за окно Y секунд, длительность open) выносятся в конфигурацию и настраиваются по данным нагрузочного тестирования.

## 3. Таймауты и deadline

- Deadline вызова `EvaluateAuction` выставляет Ad Server (30–40 мс, `bidding-service.md`) — часть общего бюджета ≤ 80 мс.
- Deadline **распространяется по цепочке** (deadline propagation): остаток бюджета передаётся дальше, ни один нижестоящий вызов не может превысить оставшееся время.
- Истечение deadline трактуется как ошибка → `no-bid` (см. `sequence-dsp-bid.puml`, ветка «Ad Server / Bidding Service — ошибка или таймаут»).

## 4. Retry

Ретраи применяются в следующих местах:

| Путь                                                | Политика ретраев                                                                                      |
|-----------------------------------------------------|-------------------------------------------------------------------------------------------------------|
| Bidding → Kafka (публикация событий)                | Retry с exponential backoff + jitter; события идемпотентны по `request_id`, потеря недопустима.       |
| Dashboard → Financial (списания/счета)              | Retry с exponential backoff + jitter; безопасно за счёт idempotency key.                              |
| Прогрев read-model при старте (Bidding → Campaigns) | Retry с backoff при недоступности Campaigns; инстанс не проходит readiness, пока прогрев не завершён. |

Exponential backoff + jitter — задержка между попытками растёт экспоненциально (например, база × 2ⁿ) с добавлением случайного разброса (jitter), чтобы одновременно перезапущенные клиенты не создавали синхронный всплеск нагрузки на восстановившийся сервис.

## 5. Идемпотентность финансовых операций

В Financial Service операции списания/выставления счетов должны быть безопасны к повторам (сетевой ретрай, повтор со стороны Advertiser Dashboard), см. `interaction.md`.

Детали механизма:
- Idempotency key — клиент (Advertiser Dashboard) генерирует уникальный ключ на бизнес-операцию (например, UUID на попытку списания) и передаёт его в заголовке запроса.
- Дедупликация — Financial Service хранит обработанные ключи с результатом операции. При повторе с тем же ключом возвращается сохранённый результат.
- Атомарность — проверка ключа и списание выполняются в одной транзакции, чтобы исключить гонку при параллельных повторах.

## 6. Failover-стратегия по компонентам

Circuit Breaker, таймауты и retry защищают критичный путь на уровне *вызовов*. Failover — это уровень *инфраструктуры*: переключение на резервный экземпляр/реплику при отказе основного, без нарушения SLA. Режим выбирается по типу состояния компонента (stateless vs stateful) и по цене потери данных.

| Компонент                      | Режим failover                                   | Обоснование                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
|--------------------------------|--------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Bidding Service                | Active-Active                                    | Сервис stateless (состояние вынесено в Redis read-model, `bidding-service.md`). N инстансов за балансировщиком обслуживают трафик одновременно; отказавший инстанс выводится из пула по HealthCheck, остальные принимают нагрузку без переключения. Даёт горизонтальное масштабирование и мгновенный failover.                                                                                                                                                             |
| Campaigns Service (PostgreSQL) | Master–Slave, асинхронная реплика, авто-failover | Source of truth конфигурации. Запись (CRUD) на master, чтение со slave; при отказе master slave промоутится автоматически. Асинхронная репликация допустима — конфигурация не финансовая, небольшой лаг репликации приемлем (см. `Task3/scaling.md`).                                                                                                                                                                                                                      |
| Financial Service (PostgreSQL) | Master–Slave, синхронная реплика, авто-failover  | Потеря денежных данных недопустима. Синхронная реплика подтверждает коммит до ответа клиенту → при failover не теряется ни одна транзакция; slave выступает горячим резервом. Дополняется идемпотентностью операций (см. раздел 5).                                                                                                                                                                                                                                        |
| Kafka                          | RF ≥ 3, `min.insync.replicas=2`, `acks=all`      | Кластер брокеров с репликацией партиций. `acks=all` в связке с `min.insync.replicas=2` означает: продюсер получает подтверждение только когда запись реплицирована минимум на 2 брокера, поэтому отказ одного брокера не теряет события (`auction-events`, `campaign-changes`), для которых потеря недопустима (см. параграф 4). RF ≥ 3 позволяет пережить отказ брокера, сохранив кворум записи.                                                                          |
| Redis (read-model)             | Cluster                                          | Данные read‑model хранятся в Redis Cluster, где они автоматически шардируются по слотам между master‑нодами (горизонтальное масштабирование под объём кампаний/ставок и под read-нагрузку hot path) и держит реплики на каждый шард с автоматическим промоушеном при отказе master (высокая доступность). Оба свойства критичны для текущего решения: read-model на hot path каждого bid-запроса, поэтому нужен и рост под нагрузку, и failover без ручного вмешательства. |

## 7. Fallback-стратегия

Единая стратегия деградации на критичном пути аукциона — это возврат `no-bid`: если Circuit Breaker `open` (Gateway или Ad Server→Bidding), таймаут/ошибка вызова, недоступность Redis read-model, то партнёру отдаётся `no-bid`.
Возврат закешированных (cached) или дефолтных ставок (default bids) при деградации не применяется, так как это повышает риски перерасхода бюджета кампании (списание по неактуальной цене/остатку бюджета) и показа неактуального ставок.
