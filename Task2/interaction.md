# Interaction — протоколы и паттерны взаимодействия

## 1. Обзор

| Связь                                                  | Протокол                                     | Синхронность | Обоснование                                                                           |
|--------------------------------------------------------|----------------------------------------------|--------------|---------------------------------------------------------------------------------------|
| Ad Server → Bidding Service                            | **gRPC** (HTTP/2, protobuf)                  | Синхронно    | Критичный путь, критично по latency                                                   |
| Advertiser Dashboard ↔ Financial / Analytics Service   | **REST** (HTTP/JSON)                         | Синхронно    | CRUD, не критично по latency                                                          |
| Advertiser Dashboard ↔ Campaigns Service               | **REST** (HTTP/JSON)                         | Синхронно    | CRUD кампаний/бюджетов/ставок, не критично по latency                                 |
| Campaigns Service → Bidding Service (read-model)       | **Kafka** (`campaign-changes`)               | Асинхронно   | Обновление/инвалидация Redis read-model ставок                                        |
| Bidding Service → Statistics / Analytics               | **Kafka** (`auction-events`)                 | Асинхронно   | Развязка critical path от write-нагрузки                                              |
| Kafka (`auction-events`) → Delivery Service            | **Kafka**                                    | Асинхронно   | Delivery получает победителя для отложенной генерации HTML/JS-разметки                |
| Delivery Service → Kafka (`ad-events`)                 | **Kafka**                                    | Асинхронно   | Delivery Service больше не делает Internal Call в Statistics Service и не ждёт записи |
| Пользователь ↔ Delivery Service                        | **HTTPS**                                    | Синхронно    | Отдача баннера и приём показов/кликов                                                 |
| Statistics Service (consumer `ad-events`) → PostgreSQL | Batched / buffered write                     | Асинхронно   | Устраняет прямую запись без буферизации                                               |
| DSP-партнёр ↔ AdScale                                  | **HTTPS / OpenRTB (JSON)** через API Gateway | Синхронно    | Требование площадки                                                                   |


## 2. Внутреннее взаимодействие с помощью gRPC и REST

### Протокол gRPC для Ad Server и Bidding Service

- Бинарная сериализация (protobuf) — заметно меньше накладных расходов на (де)сериализацию, чем JSON, особенно при высоком RPS.
- Эта связь на пути, критичном по latency

### Протокол REST для Financial, Analytics, Campaigns и Advertiser Dashboard

- Операции CRUD-характера (создание кампании, просмотр отчётности, управление балансом) — REST/JSON для этого — устоявшийся, простой в отладке и поддержке подход.
- CRUD кампаний, бюджетов и ставок обслуживает Campaigns Service — владелец (source of truth) конфигурации кампаний. Отсюда изменения записываются в read-model ставок.
- Advertiser Dashboard это веб-интерфейс (Node.js + JS), и для браузерного клиента REST/JSON — более естественный выбор, чем gRPC.
- Эти связи не находятся на критичном по latency пути аукциона
- Операции с Financial Service (списание, выставление счетов) выполняются с idempotency key, чтобы повторные запросы (сетевой ретрай, повтор со стороны Advertiser Dashboard) не приводили к двойному списанию средств.


## 3. Потоковая обработка событий с помощью Kafka

Kafka наилучшим образом подходит для потоковой обработки событий в реальном времени. В контексте системы AdScale Kafka дает следующие преимущества:
- Развязка производителя и потребителя нагрузки. Сейчас Statistics Service пишет в Postgres напрямую и синхронно, конкурируя за ресурсы БД с транзакционными операциями (ставки, финансы). Kafka вводит буфер: критичный путь (Bidding Service, Ad Server) публикует событие и не ждёт подтверждения записи в БД.
- Одно и то же событие (например, `auction-events`) независимо читают Statistics и Analytics — без дублирования логики публикации и без прямой связи "точка-точка" между Bidding Service и каждым из потребителей (снижает связность, соответствует требованию "изменяемость/модифицируемость" и пути к событийно-ориентированной архитектуре через год).
- Отсутствие потери данных. В отличие от синхронного вызова, при временной недоступности потребителя (например, перегруз Analytics) данные не теряются и не блокируют производителя — они остаются в топике до вычитывания.
- `Delivery Service` — это stateless-сервис без собственной БД. Он читает `auction-events` (победитель аукциона) из Kafka для отложенной генерации HTML/JS-разметки баннера, а событие показа/клика публикует в Kafka-топик `ad-events` — асинхронно, не дожидаясь подтверждения записи. Так он перестаёт делать синхронный `Internal Call` в `Statistics Service` и не блокируется на регистрации события.
- `Statistics Service` становится Kafka-консьюмером: читает `ad-events` и пишет в PostgreSQL батчами, а не по одной синхронной транзакции на событие.
- `Campaigns Service` при изменении кампании/бюджета/ставки публикует событие в топик `campaign-changes`. `Bidding Service` (консьюмер) применяет его к своему локальному Redis read-model. Так write-сторона Campaigns асинхронно обновляет read-сторону Bidding, не создавая прямой синхронной связи и не затрагивая hot path.


## 4. Внешнее взаимодействие и протокол интеграции с DSP

OpenRTB поверх HTTPS/JSON — это требование партнёра. Внутри AdScale, сразу за границей протокола (в Ad Server), запрос преобразуется во внутреннее представление и далее идёт по gRPC.

API Gateway нужен на границе с DSP-партнёром, так как
- Нужна единая точка аутентификации партнёра, не размазанная по коду Ad Server.
- Нужен rate limiting на уровне контракта с партнёром (SLA/квоты).
- Нужен Circuit Breaker и единая точка, где можно быстро вернуть "no-bid" при деградации бэкенда, не роняя сам Ad Server.
- Нужен единый срез метрик времени отклика именно на границе, которую измеряет партнёр.
