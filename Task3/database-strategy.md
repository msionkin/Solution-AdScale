# Database per Service — стратегия данных

В целевой микросервисной архитектуре (через год, 50 000 RPS, SLA 99,9%) у каждого сервиса своё хранилище (Database per Service), чтобы убрать единый PostgreSQL как узкое место и Single Point of Failure и разделить критичные/некритичные потоки.

**Выбор базы данных по сервисам:**

| Сервис                             | Тип базы данных                                                                                       | Обоснование                                                                                                                                                                                                                                                    |
|------------------------------------|-------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Сервис ставок** (Bidding)        | Собственной СУБД нет. Read-model в **Redis** (in-memory KV)                                           | Hot path, критично по latency (≤80 мс). Сервис stateless, синхронно не читает Postgres — только реплику ставок/кампаний из локального Redis, результат публикует в Kafka. Read-model восстанавливается из Сервиса кампаний, поэтому персистентная БД не нужна. |
| **Сервис кампаний** (Campaigns)    | **PostgreSQL** (реляционная OLTP)                                                                     | Source of truth для кампаний, бюджетов и ставок. Данные связные (рекламодатель → кампания → объявление), нужны транзакции и целостность при CRUD из Advertiser Dashboard. Изменения отсюда наполняют read-model ставок.                                        |
| **Сервис статистики** (Statistics) | **PostgreSQL** — выделенный инстанс, оптимизированный на запись (батчи, партиционирование по времени) | Поток событий показов/кликов. Консьюмер Kafka пишет батчами, а не по одной транзакции. Отдельный инстанс убирает конкуренцию write-нагрузки с OLTP (ставки/финансы). Append-only + партиции по дате упрощают ротацию и масштаб записи.                         |
| **Сервис аналитики** (Analytics)   | **PostgreSQL read-replica(s)**                                                                        | Тяжёлые аналитические запросы не должны блокировать критичный путь и запись событий. Данные производные (можно перестроить), поэтому это отдельный read-контур поверх реплик статистики/кампаний.                                                              |
| **Сервис финансов** (Financial)    | **PostgreSQL** (реляционная OLTP, ACID)                                                               | Здесь нужны строгие транзакции и согласованность. Операции идемпотентны (по idempotency key) для защиты от двойного списания при ретраях. Изоляция от аналитики/статистики обязательна.                                                                        |

Такое распределение баз по сервисам позволяет:
- Изолировать данные - сервисы не ходят в чужие БД. Обмен — через Kafka (события) и REST/gRPC (синхронные запросы).
- Разделить потоки - критичный путь (ставки) не имеет синхронной БД; статистика/аналитика вынесены на отдельные хранилища, их нагрузка не влияет на аукцион.
- Реализовать отдельное масштабирование операций чтения и записи с помощью CQRS: Сервис кампаний — write-модель с PostgreSQL, Сервис ставок — read-модель в Redis.
