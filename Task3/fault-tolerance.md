# Отказоустойчивость данных

Цель: SLA 99,9%, отсутствие простоев Bidding сервиса, непрерывность бизнеса и защита от потери данных (особенно финансовых).

## 1. RPO / RTO по сервисам

- **RPO (Recovery Point Objective)** — сколько данных допустимо потерять (за какой момент времени восстановимся). Задаёт частоту бэкапа/репликации.
- **RTO (Recovery Time Objective)** — за какое время сервис должен снова работать. Задаёт «горячесть» резерва.

| Сервис         | RPO                            | RTO       | Обоснование и как достигается                                                                                                                                                       |
|----------------|--------------------------------|-----------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Финансов**   | ≈ 0 (потеря денег недопустима) | ≤ 1 мин   | Синхронная реплика + ACID + идемпотентность по `idempotency key`. Ни одна транзакция не теряется; авто-failover master→slave без потери данных.                                     |
| **Ставок**     | 0 (собственных данных нет)     | ≤ 30 сек  | Stateless: read-model восстанавливается из Сервиса кампаний и `campaign-changes` в Kafka (прогрев кэша). Простой недопустим → мультирегион / Active-Active, добавление инстансов.   |
| **Кампаний**   | ≤ 5 мин                        | ≤ 15 мин  | Source of truth конфигурации. PostgreSQL Master–Slave + непрерывный WAL + PITR; failover на реплику.                                                                                |
| **Статистики** | ≤ 5 мин                        | ≤ 1 час   | События буферизуются в Kafka (replay), поэтому при сбое БД поток не теряется — RPO обеспечивается реплеем, а не только бэкапом. Восстановление батч-консьюмера с последнего offset. |
| **Аналитики**  | ≤ 24 часа                      | ≤ 24 часа | Данные производные, перестраиваются из событий/статистики; вне критичного пути, поэтому допуски высокие.                                                                            |

## 2. Стратегия резервного копирования (backup)

| Хранилище                   | Стратегия                                                                                                | RPO                   |
|-----------------------------|----------------------------------------------------------------------------------------------------------|-----------------------|
| **PostgreSQL — Финансы**    | Синхронная реплика (горячий резерв) + непрерывный WAL-архив + PITR + ежедневный full-снапшот             | ≈ 0                   |
| **PostgreSQL — Кампании**   | Непрерывный WAL-архив + PITR + ежедневный full-снапшот; асинхронные реплики для чтения                   | ≤ 5 мин               |
| **PostgreSQL — Статистика** | Full-снапшот раз в сутки + WAL/incremental по шардам; основной источник восстановления — реплей из Kafka | ≤ 5 мин (реплей)      |

Про PITR (Point-in-Time Recovery). Для реляционных БД (кампании, финансы) непрерывно архивируется WAL поверх периодических полных снапшотов. Это даёт восстановление на любой момент времени (например, «за секунду до сбойной миграции» или до логической ошибки/удаления данных).

Долгое хранение (архив). Для финансов/аудита применяется схема Grandfather-Father-Son: ежедневные инкременты (Son), еженедельные полные копии (Father), ежемесячные полные копии на длительное хранение (Grandfather) — позволяет откатиться на любую дату в рамках регуляторных требований.

## 3. DR-план (Disaster Recovery)

### 3.1. Высокоуровневый DR-план

- Мультирегиональное развёртывание: должен быть основной регион (Primary) и регион аварийного восстановления (DR).
- Сервис ставок — Active-Active в двух регионах (RTO в секундах, недопустим простой): трафик балансируется, при потере региона DSP обслуживается оставшимся.
- Финансы / Кампании — Warm Standby: синхронная (финансы) / асинхронная (кампании) репликация PostgreSQL в DR-регион, готовая реплика для промоушена в master.
- Kafka — кластер с `RF ≥ 3`, распределённый по availability-зонам.
- Бэкапы — хранилище с гео-репликацией.

### 3.2. Сценарии отказа и реакция

| Сценарий                                   | RPO / RTO          | Реакция                                                                                                  |
|--------------------------------------------|--------------------|----------------------------------------------------------------------------------------------------------|
| Падение инстанса сервиса (stateless)       | 0 / секунды        | Оркестратор (K8s) перезапускает pod; трафик уходит на здоровые инстансы.                                 |
| Отказ master PostgreSQL (финансы/кампании) | ≈ 0 / ≤ 1–15 мин   | Авто-failover: промоушен синхронной/асинхронной реплики в master.                                        |
| Потеря шарда статистики                    | ≤ 5 мин / ≤ 1 час  | Восстановление шарда из снапшота + реплей событий из Kafka с последнего offset.                          |
| Отказ Redis                                | 0 / секунды–минуты | Read-model прогревается заново из Сервиса кампаний; сервис ставок держит трафик по мере наполнения кэша. |

## 4. Проверка на соответствие 12-факторным приложениям

Оценка целевой архитектуры по каждому из 12 факторов и его вкладу в отказоустойчивость / восстановление.

| #    | Фактор                          | Соответствие в AdScale                                               | Вклад в отказоустойчивость                                               |
|------|---------------------------------|----------------------------------------------------------------------|--------------------------------------------------------------------------|
| I    | Кодовая база                    | Один репозиторий на сервис, один и тот же артефакт во все окружения. | Воспроизводимое развёртывание в DR-регионе из той же кодовой базы.       |
| II   | Зависимости                     | Явные манифесты, установка одной командой, фиксированные версии.     | Идентичное окружение при восстановлении инстанса/региона.                |
| III  | Конфигурация                    | Адреса БД/Redis/Kafka и credentials — в переменных окружения.        | Переключение на реплику/DR-эндпоинт без изменения и пересборки кода.     |
| IV   | Сторонние службы                | PostgreSQL/Redis/Kafka — присоединённые ресурсы.                     | Реплику или failover-инстанс подставляем как замену ресурса.             |
| V    | Сборка, выпуск, запуск          | Раздельные стадии, неизменяемый релиз-артефакт.                      | Быстрый и предсказуемый откат/повторный запуск при инциденте.            |
| VI   | Процессы                        | Сервисы stateless (особенно Ставки); состояние — в backing services. | Инстанс можно потерять/пересоздать без потери данных.                    |
| VII  | Привязка портов                 | Сервисы самодостаточны, экспортируют порт (gRPC/HTTP).               | Легко масштабировать/переносить за балансировщик, в т.ч. в DR.           |
| VIII | Конкурентность                  | Горизонтальное масштабирование инстансов и consumer-групп Kafka.     | Резервирование мощности и параллельная обработка под нагрузкой.          |
| IX   | Утилизируемость                 | Быстрый старт (прогрев кэша) + graceful shutdown Kafka-консьюмеров.  | Быстрый RTO, безопасный перезапуск и авто-восстановление.                |
| X    | Среды разработки и эксплуатации | Одинаковые контейнеры/инструменты в dev/stage/prod.                  | Отсутствие неожиданных проблем в разных средах.                          |
| XI   | Логи                            | Логи как потоки событий в stdout → централизованный сбор.            | Наблюдаемость сбоев и восстановление контекста без локального состояния. |
| XII  | Админ-процессы                  | Миграции/бэкап-задачи — одноразовые процессы в том же окружении.     | Управляемое восстановление данных (в т.ч. запуск PITR/реплея) как код.   |
