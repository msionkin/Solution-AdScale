# Кэширование

Цель - снять синхронные обращения к БД с критичного пути аукциона и удержать ≤80 мс на 50 000 RPS.

## Кэширование с помощью Redis

Кэшировать необходимо:
- Кампании — активные кампании и их таргетинг.
- Бюджеты — остатки бюджетов.
- Ставки (bid data) — заявленные ставки кандидатов.

Это read-model Bidding Service - `EvaluateAuction` читает данные только из Redis, а не из Postgres.

Redis необходимо разместить рядом с Bidding Service (в том же регионе/пуле), тогда получим минимальную сетевую задержку.

## TTL и инвалидация

| Данные                      | TTL                          | Инвалидация                                                                                                              |
|-----------------------------|------------------------------|--------------------------------------------------------------------------------------------------------------------------|
| Кампании (конфиг/таргетинг) | средний (напр. минуты–часы)  | Событийная - при изменении в Campaign Service публикуется событие, тогда консьюмер обновляет Redis. TTL — как страховка. |
| Бюджеты (остатки)           | короткий                     | Событийная + короткий TTL: бюджет может меняться часто                                                                   |
| Ставки                      | средний                      | Событийная при изменении кампании.                                                                                       |


## Прогрев кэша (cache warming)

При старте нового инстанса Bidding Service Redis наполняется активными кампаниями и ставками до принятия трафика. Инстанс Bidding Service проходит readiness (`HealthCheck`) только после прогрева. Прогрев происходит из Campaign Service.

См. диаграмму `diagrams/data-architecture.puml`.
