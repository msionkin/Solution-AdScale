# Масштабирование баз данных

Цель - обеспечить 50 000 RPS и SLA 99,9%, убрав единый PostgreSQL как узкое место и точку отказа.

## Репликация Master–Slave

| Сервис         | Репликация                        | Обоснование                                                                                                |
|----------------|-----------------------------------|------------------------------------------------------------------------------------------------------------|
| **Financial**  | Master–Slave, синхронная реплика  | HA для денежных транзакций позволит реализовать авто-failover без потери данных; slave как горячий резерв. |
| **Campaigns**  | Master–Slave, асинхронные реплики | Запись (CRUD) на master; чтение конфигурации/отчётности — со slave. Реплики нужны для read-model ставок.   |
| **Statistics** | Master–Slave на каждом шарде      | Отказоустойчивость append-контура; чтение агрегатов со slave, не мешая батч-записи.                        |

## Шардирование

Шардируется только высоконагруженный на запись Statistics Service (события показов/кликов). Ключ шардирования - `campaign_id`. Распределяет write-нагрузку и позволяет считать статистику по кампании локально в шарде. Партиционирование по времени (дата) внутри шарда. Упрощает ротацию/архивирование старых событий и ускоряет запись append-only.

## Read replicas

Read replicas необходимы для аналитики. Сервис аналитики должен работать только с read-replica (реплики статистики/кампаний), а не с master. Тогда тяжёлые аналитические запросы не будут блокировать критичный путь и запись событий (устраняет проблему AS-IS — блокировки на production-БД). Плюс реплики можно масштабировать независимо под рост объёма отчётов.

## CQRS 

Применяется там, где необходима разделённая модель чтения и записи для масштабирования:
- Campaigns (write) ↔ Bidding (read): Campaigns Service — command-сторона (source of truth в PostgreSQL). Bidding Service — query-сторона: денормализованный read-model в Redis, обновляется из событий изменения конфигурации.
- Statistics (write) ↔ Analytics (read): события пишутся в статистику (батчи), а отчётность строится по read-репликам/аналитическому контуру. Kafka — канал распространения между сторонами.
